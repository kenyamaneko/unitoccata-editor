# リリース手順

dev と prod への反映の手順。配信先は、どちらも Firebase Hosting。Firestore と Storage の規則は、この手順では配備しない (Terraform が各環境へ反映する)。

どの種類のバージョンアップを選ぶかは、keyandnotes-rules のバージョニングとCI方針に従う。

## dev へ反映する

main へマージ (プッシュ) すると、GitHub Actions の「Deploy to Dev」が自動で動き、dev へデプロイする。人の操作は要らない。

「Deploy to Dev」は次のジョブで構成される。

1. **「CI」と「バージョンの判定」**：並行して動く。「バージョンの判定」は `git describe --tags --always` の結果をバージョンにする
2. **「Firebase Hosting を dev へデプロイ」**：「CI」と「バージョンの判定」が成功したあとに、ビルドして `npx firebase-tools deploy --only hosting` を実行する
3. **「デプロイ後のスモークテスト (dev)」**：デプロイが成功したあとに実行する

「テスト観点カタログとカバレッジを GitHub Pages へ公開する」は、「CI」が成功したあとに、デプロイと並行して動く。

押さえておく挙動は次のとおり。

- 変更が `*.md`・`docs/`・`rules/`・`.claude/` のファイルだけのプッシュでは、「Deploy to Dev」は動かない
- main へ続けてプッシュすると、実行中の「Deploy to Dev」は取り消され、あとのプッシュの実行だけが残る
- main へのプッシュでは、単独の「CI」も同時に始まり、「Deploy to Dev」の中の「CI」と同じ並行実行の枠に入るため取り消される。取り消された単独の「CI」の表示は異常ではない
- GitHub の Actions 画面の「Run workflow」で手動実行もできる。このとき dev へ反映されるのは、実行時に選んだブランチの内容

## prod へリリースする

prod へのリリースは、人が「Deploy to Prod」を実行して始める。

### 実行前に確かめること

- 反映したい変更が main にマージされている
- main の最新のコミットの「Deploy to Dev」が、スモークテストまで成功している。最新のコミットが上の「動かない」変更だけのときは、「Deploy to Dev」が動いた直近のコミットの実行を見る

「Deploy to Prod」は「CI」を実行しない。実行した時点の main の最新のコミットをビルドして、prod へデプロイする。

### 実行する

1. GitHub の Actions 画面で、左の一覧から「Deploy to Prod」を選ぶ
2. 「Run workflow」を押し、ブランチに `main` を選ぶ
3. `bump` (Version bump level) で、`patch`・`minor`・`major` のどれかを選ぶ (初期値は `patch`)
4. 「Run workflow」を押して実行する

### 実行中に起きること

「Deploy to Prod」は次の順で進む。

1. **「バージョンのタグ付け」**：CI が次のタグを決めて、main の最新のコミットに打ち、リポジトリへプッシュする。タグは人が打たない
2. **「バージョンの判定」**：`git describe --tags --always` の結果をバージョンにする
3. **「Firebase Hosting を prod へデプロイ」**：ビルドして `npx firebase-tools deploy --only hosting` を実行する
4. **「デプロイ後のスモークテスト (prod)」**：デプロイが成功したあとに実行する

次のタグは、`v` で始まるタグのうちバージョンが最も新しいものと、選んだ `bump` から、CI が決める。

### バージョンタグが 1 つも無いとき

`bump` に何を選んでも、最初のタグは `v0.1.0` になる。

### main 以外で実行したとき

「バージョンのタグ付け」が実行されず、それに続く「バージョンの判定」・「Firebase Hosting を prod へデプロイ」・「デプロイ後のスモークテスト (prod)」もスキップされる。

main 以外のコミットにタグを打って prod に出さないための動きなので、リリースするときは `main` を選んで実行し直す。

### 実行が重なったとき

「Deploy to Prod」は同じブランチで同時に 1 つしか動かない。実行中にもう一度実行すると、あとの実行は先の実行が終わるまで待つ。先の実行は取り消されない。待っている実行がある間にさらに実行すると、待っていた実行が取り消され、最後の実行だけが待つ。取り消された実行はタグを打たない。

### デプロイが失敗したとき

「Firebase Hosting を prod へデプロイ」が失敗しても、「バージョンのタグ付け」で打ったタグは残る。「Deploy to Prod」を新しく実行すると、タグがもう 1 つ増える。

## デプロイ後に確かめること

「Deploy to Dev」と「Deploy to Prod」は、デプロイのあとにスモークテストを実行する。スモークテストは、デプロイ済みの環境 (`https://{プロジェクト ID}.web.app`) を実際のブラウザ (Chromium) で開いて、次を確かめる。

| 確かめること                | 成功の条件                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ |
| エディタの表示              | URL を開くと、タイムラインと、右のパネルの「ファイル」ボタンが表示される                                    |
| バージョンの表示            | 「このアプリについて」のダイアログのバージョンが、`v` で始まるタグの形式か、短縮したコミット ID で表示される |
| Google ログイン画面への接続 | 「ログイン」から「Google でログイン」を押すと、`accounts.google.com` のウィンドウが開く                      |
| Firestore の読み取り権限    | 未ログインで利用者のプロジェクトの一覧を読むと、HTTP ステータス 403 と `PERMISSION_DENIED` が返る           |
| Storage の読み取り権限      | 未ログインで利用者のファイルの一覧を読むと、HTTP ステータス 401 か 403 が返る                                |

ログインそのものは行わない。

### スモークテストが失敗したとき

失敗しても、デプロイ済みの Hosting は元に戻らない。

1. GitHub の Actions 画面で、失敗した実行を開く
2. 「デプロイ後のスモークテスト」のジョブを開き、「スモークテストを実行する」のステップのログを見る。失敗したテストの名前と、期待した値と実際の値が出ている
3. ログに `環境変数 … がありません` と出ているときは、テストを始める前に止まっている。対象の環境 (dev または prod) の変数 `FIREBASE_PROJECT_ID`・`FIREBASE_STORAGE_BUCKET` が設定されているか確かめる

スモークテストの結果のファイル (`test-results/smoke-junit.xml`) は、成果物としては保存されない。ログだけが手がかりになる。

手元からスモークテストを実行する方法は、セットアップ手順書の「スモークテスト」にある。
